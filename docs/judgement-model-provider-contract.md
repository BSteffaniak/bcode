# Judgement model provider contract (in progress)

`bcode.judgement-model-provider/v1` is a non-conversational, typed service separate from `bcode.model-provider/v1–v3`. It describes one bounded judgement over an application-provided state and a map of caller-owned question IDs. Providers advertise question kinds on both the provider and individual model; absent support is not inferred. A judgement provider does not acquire turn-stream, tool-call or chat capabilities by advertising this interface.

Portable types live in `bcode_model::judgement`: `State`, `Question` (Choice, Score, YesNo), `Answer`, `ModelList`, `Request`, `Response` and `Usage`. TypeSafe's wire schema is *not* this service's schema. Unknown question kinds fail decoding; unsupported kinds fail capability checks. Responses require exactly the requested IDs, matching answer kinds, finite in-range numeric values and consistent option IDs/cardinality. Encoded requests and responses are limited to 256 KiB, batches to 64 questions, and choice/rubric options to 128. Provider transports may enforce stricter limits.

Service operations: `models` advertises the provider and its model capabilities; `judge` accepts the typed request and returns a typed response. Interface IDs delimit compatibility; unsupported future interfaces and variants fail closed rather than being treated as v1. Providers should ignore additive, non-semantic request fields, but must not silently reinterpret unsupported semantic controls. Public failures must be normalized, bounded and secret-safe. Do not persist judgement input, credentials or vendor-native metadata as session turns.

The loop plugin offers optional judgement-backed per-iteration completion evaluation; see [Judgement evaluation in goals and loops](loop-judgement-evaluation.md). This does not change goal readiness, chat routing or the provider-neutral contract.

**Implementation status:** portable contract and catalog resolver, typed client/IPC/server route, fake provider and TypeSafe/Jev plugin exist. The application accepts either an explicit provider-owned auth profile or an explicit empty profile selecting an enabled plugin's declared process-environment credentials (no implicit selection or chat routing change), and invokes the judgement service with a bounded timeout. IPC carries bounded JSON because the binary codec cannot decode JSON `Value`/tagged questions directly. Jev bounds HTTP reads, checks outbound size/response identity, and fake-loopback tests cover authenticated discovery, judgement, oversized responses and safe upstream auth errors. The plugin observes host service cancellation during discovery and judgement; a loopback HTTP test verifies cancellation closes a stalled discovery response socket when its runtime exits. Daemon application-route and loopback IPC client tests confirm a fake provider returns typed answers and usage with an owned auth profile; disabled/missing provider calls fail closed. The IPC handler drops transient judgement work on connection loss; an in-flight pending-future test verifies dropping the operation. A live `BcodeClient::judge` → daemon → Jev plugin call to the website API passed via the ignored, explicitly opt-in `judgement_client_ipc_live_jev` test using a temporary `JEV_API_KEY` in the daemon/test process environment with no stored auth profile: it returned a validated YesNo probability and usage. Direct bounded HTTPS calls to the same host returned HTTP 200 with mixed Choice/Score/Noul answers and usage; `jev-latest` resolved to `jev-1.13.0`. The separate `api.typesafe.ai` host returned 403/401 and is not the website-key endpoint. Jev's default endpoint now targets the website API and advertises only the verified alias and resolved model; that host did not expose a working model-list endpoint, so discovery checks credential presence but cannot validate the key. Loopback client→daemon→Jev tests remain as deterministic coverage. Temporary key revocation remains unconfirmed; revoke it through the authorized TypeSafe account.
